Aula 3

O que você vai sair sabendo

  • O que são constraints e por que importam
  • Usar PRIMARY KEY pra identificar registros
  • Usar FOREIGN KEY pra ligar tabelas
  • Garantir não duplicação com UNIQUE
  • Validar regras com CHECK
  • Definir valor padrão com DEFAULT
  • Adicionar e remover constraints com ALTER TABLE
Conceito

Regras escritas no schema

O banco passa a recusar dado que não respeite as regras.

Sem constraints

Aplicação confia que o dado tá correto. Bug no front? Dado lixo no banco. Múltiplas apps escrevem? Cada uma valida do seu jeito.

Com constraints

Regra fica no schema, não no código. Funciona pra qualquer aplicação que escreva. Inconsistência vira erro imediato, não bug silencioso.

Regra de ouro Não confie só na aplicação. O banco é a última linha de defesa.
Identificação

PRIMARY KEY

Identificador único e obrigatório de cada linha.

-- Forma inline (na criação da tabela)
CREATE TABLE contas (
  id            INT IDENTITY(1,1) PRIMARY KEY,
  login         NVARCHAR(50) NOT NULL,
  email         NVARCHAR(120) NOT NULL
);

-- Forma com nome (recomendada)
CREATE TABLE contas (
  id            INT IDENTITY(1,1) NOT NULL,
  login         NVARCHAR(50) NOT NULL,
  email         NVARCHAR(120) NOT NULL,
  CONSTRAINT PK_contas PRIMARY KEY (id)
);
Características PK é sempre NOT NULL, sempre UNIQUE, e cria um índice automático. Cada tabela tem uma PK só.
Ligando tabelas

FOREIGN KEY

Referência para outra tabela. Banco garante que o id realmente existe.

CREATE TABLE personagens (
  id            INT IDENTITY(1,1) NOT NULL,
  conta_id      INT NOT NULL,
  classe_id     INT NOT NULL,
  nome          NVARCHAR(60) NOT NULL,
  CONSTRAINT PK_personagens PRIMARY KEY (id),
  CONSTRAINT FK_personagens_contas
    FOREIGN KEY (conta_id) REFERENCES contas(id),
  CONSTRAINT FK_personagens_classes
    FOREIGN KEY (classe_id) REFERENCES classes(id)
);
Banco vai recusar INSERT em personagens com conta_id que não existe em contas. E não deixa deletar uma conta que tem personagens (a menos que configure ON DELETE, vamos ver na Aula 3.5).
Sem duplicatas

UNIQUE

Garantir que nenhum valor se repita naquela coluna.

-- Login e email não podem repetir entre contas
CREATE TABLE contas (
  id            INT IDENTITY(1,1) NOT NULL,
  login         NVARCHAR(50) NOT NULL,
  email         NVARCHAR(120) NOT NULL,
  CONSTRAINT PK_contas PRIMARY KEY (id),
  CONSTRAINT UQ_contas_login UNIQUE (login),
  CONSTRAINT UQ_contas_email UNIQUE (email)
);
PK vs UNIQUE PK também é único, mas é o identificador principal. UNIQUE serve pra outras colunas que precisam ser únicas (login, email, CPF, etc).
Validando regras

CHECK

Regra customizada que cada linha precisa respeitar.

CREATE TABLE personagens (
  id            INT IDENTITY(1,1) NOT NULL,
  nome          NVARCHAR(60) NOT NULL,
  nivel         SMALLINT NOT NULL,
  vida_max      INT NOT NULL,
  CONSTRAINT PK_personagens PRIMARY KEY (id),
  CONSTRAINT CK_personagens_nivel CHECK (nivel BETWEEN 1 AND 100),
  CONSTRAINT CK_personagens_vida CHECK (vida_max > 0)
);
Exemplos de uso Valor monetário positivo, data de fim depois da data de início, status dentro de uma lista de valores válidos.
Valor padrão

DEFAULT

Se ninguém passar valor, o banco preenche com esse.

CREATE TABLE contas (
  id            INT IDENTITY(1,1) NOT NULL,
  login         NVARCHAR(50) NOT NULL,
  ativo         BIT NOT NULL DEFAULT 1,
  data_criacao  DATETIME NOT NULL DEFAULT GETDATE(),
  CONSTRAINT PK_contas PRIMARY KEY (id)
);

-- Agora dá pra inserir sem passar ativo nem data_criacao
INSERT INTO contas (login) VALUES ('arthas');
Combina bem com NOT NULL Coluna obrigatória, mas com valor automático. Você não precisa lembrar de preencher.
Adicionando depois

Quando a tabela já existe

Dá pra adicionar e remover constraints sem recriar a tabela.

-- Adicionar PRIMARY KEY
ALTER TABLE contas
ADD CONSTRAINT PK_contas PRIMARY KEY (id);

-- Adicionar FOREIGN KEY
ALTER TABLE personagens
ADD CONSTRAINT FK_personagens_contas
  FOREIGN KEY (conta_id) REFERENCES contas(id);

-- Adicionar CHECK
ALTER TABLE personagens
ADD CONSTRAINT CK_personagens_nivel CHECK (nivel >= 1);

-- Remover constraint
ALTER TABLE personagens
DROP CONSTRAINT CK_personagens_nivel;
Cuidado Se a tabela já tem dados que violam a regra nova, ADD CONSTRAINT falha. Limpe os dados primeiro ou use WITH NOCHECK (avançado, evite).

Tabela contas com todas as constraints

CREATE TABLE contas (

  login         NVARCHAR(50) NOT NULL,
  email         NVARCHAR(120) NOT NULL,
  senha_hash    NVARCHAR(255) NOT NULL,
  data_criacao  DATETIME NOT NULL DEFAULT GETDATE(),
  ativo         BIT NOT NULL DEFAULT 1,
  CONSTRAINT PK_contas PRIMARY KEY (id),
  CONSTRAINT UQ_contas_login UNIQUE (login),
  CONSTRAINT UQ_contas_email UNIQUE (email),
  CONSTRAINT CK_contas_email CHECK (email LIKE '%@%.%')
);
Aplicando no RPG

Personagens com FKs e regras

CREATE TABLE personagens (
  id            INT IDENTITY(1,1) NOT NULL,
  conta_id      INT NOT NULL,
  classe_id     INT NOT NULL,
  nome          NVARCHAR(60) NOT NULL,
  nivel         SMALLINT NOT NULL DEFAULT 1,
  vida_max      INT NOT NULL,
  mana_max      INT NOT NULL,
  experiencia   BIGINT NOT NULL DEFAULT 0,
  data_criacao  DATETIME NOT NULL DEFAULT GETDATE(),
  CONSTRAINT PK_personagens PRIMARY KEY (id),
  CONSTRAINT FK_personagens_contas FOREIGN KEY (conta_id) REFERENCES contas(id),
  CONSTRAINT FK_personagens_classes FOREIGN KEY (classe_id) REFERENCES classes(id),
  CONSTRAINT CK_personagens_nivel CHECK (nivel BETWEEN 1 AND 100),
  CONSTRAINT CK_personagens_vida CHECK (vida_max > 0),
  CONSTRAINT CK_personagens_mana CHECK (mana_max >= 0)
);
Aplicando no RPG

Items com regras de negócio

CREATE TABLE items (
  id            INT IDENTITY(1,1) NOT NULL,
  nome          NVARCHAR(80) NOT NULL,
  tipo          NVARCHAR(30) NOT NULL,
  raridade      NVARCHAR(20) NOT NULL DEFAULT 'Comum',
  valor         DECIMAL(10,2) NOT NULL,
  CONSTRAINT PK_items PRIMARY KEY (id),
  CONSTRAINT UQ_items_nome UNIQUE (nome),
  CONSTRAINT CK_items_valor CHECK (valor >= 0),
  CONSTRAINT CK_items_raridade CHECK (raridade IN ('Comum', 'Incomum', 'Raro', 'Épico', 'Lendário'))
);
CHECK com IN Ótimo pra restringir um campo a uma lista fechada de valores. Alternativa a criar uma tabela separada de "raridades".
Vendo as constraints em ação

Erros úteis

O banco bloqueia o INSERT/UPDATE inválido e mostra qual constraint quebrou.

-- Tenta inserir personagem com conta inexistente
INSERT INTO personagens (conta_id, classe_id, nome, vida_max, mana_max)
VALUES (9999, 1, 'Hacker', 100, 50);
-- ERRO: violação de FK_personagens_contas

-- Tenta cadastrar duas contas com mesmo login
INSERT INTO contas (login, email, senha_hash) VALUES ('arthas', 'a@b.com', 'h');
INSERT INTO contas (login, email, senha_hash) VALUES ('arthas', 'c@d.com', 'h');
-- ERRO: violação de UQ_contas_login

-- Tenta criar personagem nível 200
INSERT INTO personagens (conta_id, classe_id, nome, nivel, vida_max, mana_max)
VALUES (1, 1, 'GodMode', 200, 100, 50);
-- ERRO: violação de CK_personagens_nivel
Boas práticas

Antes de seguir em frente

  1. Nomeie suas constraintsCONSTRAINT FK_personagens_contas é melhor que deixar o SQL Server gerar FK__personag__conta__1234ABCD. Quando der erro, fica claro qual quebrou.
  2. Padrão de nomesPK_tabela, FK_tabela_referencia, UQ_tabela_coluna, CK_tabela_coluna. Consistência ajuda a manter.
  3. Constraint no banco, não só no códigoAplicação tem bug. Pessoa nova chega e bypassa validação. Banco é a fonte da verdade.
  4. CHECK pra regras simplesLógica complexa fica difícil de manter no CHECK. Pra esses casos, considere triggers (Aula 5).
  5. Pense no impactoAdicionar constraint em tabela cheia em produção pode levar horas. Janela de manutenção.

Biblioteca: blindando o sistema

Aplique constraints em todas as tabelas da biblioteca.

  • PRIMARY KEY em todas as tabelas
  • FOREIGN KEY ligando livros → autores, empréstimos → usuários, empréstimos → livros
  • UNIQUE no nome dos livros
  • CHECK garantindo data_devolucao >= data_emprestimo
  • DEFAULT em colunas que faz sentido (data de cadastro, status)
  • Teste: tente inserir dados inválidos e veja o banco recusar
